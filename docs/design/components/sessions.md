# Session list, expanded content, and footer

<a id="sessions-membership"></a>
## Membership, ordering, filtering

**SE-01 (S/T):** Display open discovered sessions including idle. Do not substitute a history archive for live discovery. Filter by enabled application before rendering. Filtering never deletes the underlying session or stops its agent. Refresh automatically from monitor snapshots; no Refresh control in the native popup or current Telegram keyboard.

**Discovery edge case (M/G provider):** Losing rotated VS Code membership logs must not by itself hide a thread retained by that live extension host’s own Codex writer. The fallback requires the writer’s parent PID to match the currently verified host generation; explicit closed roles win. No matching live host means no fallback. This only affects list membership/workspace association; it does not establish permission or messaging capability. Sources: `codex::open`, `vscode::{writer_parents,resolve_live_with_writers}`.

M/G grouping rank: VS Code, Terminal, identified desktop applications, Unknown. Then application ID, then natural title order, then stable session key. M uses Foundation localizedStandardCompare, G uses lowercase GLib FilenameCollationKey; locale/case equivalence is not guaranteed. H fixtures are fixed within explicitly enumerated VS Code/Terminal/Codex groups, not dynamically sorted. Native list sorting and the live web projection share `platform::session_order`, using the host platform’s collation rather than the phone’s locale. The web renderer follows incoming group/session order on every snapshot, including renames and newly discovered sessions; moving existing nodes MUST preserve editor drafts, focus and selection rather than rebuild session documents. The prototype continues to follow its fixture order.

M/G/H render one flat session list, ordered first by application and then by natural title/stable session key, without application heading rows or application-group containers. A 16×16 application icon follows every session title with an 8 pt gap. At rest there is no destination arrow. Hovering or keyboard-focusing the title reveals a 14 pt right arrow before the icon (4 pt gap), moving the icon right; the title hover/focus surface includes both. The native highlight retains its existing height (`SESSION_HEADER_HEIGHT - 6`) and reserves the complete destination width. H derives the highlight width directly from its title button. The first session has its own robot just like every subsequent session. Application boundaries add no special gap or decoration; ordinary row separators continue across them. The HTML fixture preserves its supplied order; live web order is projected by the monitor host.

**SE-02 (M/H implemented; G differs):** Hiding application headings MUST NOT merge groups, change their ordering, remove robot controls, or add a separate keyboard target for the application icon. Clicking the title still opens that session in its host application. G still displays application name/icon headings; parity is pending. M resolves bundle ID/file icons, G desktop-entry/theme icons, H fixture assets; unresolved native icons use a generic application fallback.

## Working robot motion

**SE-ROBOT-01 (S, implemented H/M/G):** A working session keeps its robot at the normal 14×11 artwork size. Only its eyes animate; the head must not breathe, rotate, translate, fade, resize its row, or change its hit target. Application headings scroll independently with their groups and never cover the robot.

**SE-WORKING-01 (S, implemented H/M/G):** The working status is a static green filled disc, diameter15 within an18×18 symbol viewport, with a small solid rightward play triangle centered optically inside. H/M/G render the same6.72×8.32 filled triangle directly within the18×18 viewport. Its centroid coincides with the disc center: base at x−2.24 with endpoints y±4.16, tip at x+4.48. M uses `WorkingStatusView`, G Cairo and H inline SVG, avoiding font/symbol alignment insets. Light appearance uses white triangle ink, dark appearance uses dark green `#10351e`; disc green follows each frontend's established working palette. No outline-only triangle, rotating arrows or status animation. The glyph is informational, with “Working” tooltip/native label, and is not an actionable Play button. It must not enter answer navigation or acquire its own hover/click target. Request/finished state indicators retain their existing semantics and colors.

**SE-ROBOT-02 (S, implemented H/M/G):** Working eyes are green and cycle through left/right brightness pairs `.5/0 → 1/0 → 1/.5 → 1/1 → .5/1 → 0/1 → 0/.5 → 0/0 → repeat`, linearly interpolated across eight equal intervals of a 2.4-second cycle. Zero brightness means invisible eyes, without neutral eyes underneath. This follows the menu-bar eye pattern but uses its own slower cycle; it does not change menu-bar animation or counters. Request eyes remain orange and idle/other eyes remain neutral; these states have static eyes.

**SE-ROBOT-03 (S):** System reduced-motion disables eye animation, leaving both working eyes steadily green. H uses `prefers-reduced-motion`, M uses the workspace accessibility preference, G uses GTK's enable-animations preference. The app's *Menu bar animation* setting does not control session markers. Discovery redraws must not restart eye motion; native frontends use an owner-held monotonic epoch. Artwork, click targets and thread geometry remain fixed; native robot drawing is14×11 centered in the existing button bounds, with no extra vertical offset. The thread starts at the robot's normal contour.

## Expanded reading order and messages

Shared native reading order: header → earlier messages/current latest → active request card → folder/branch metadata. Request does not replace current message. Trailing whitespace is trimmed on message display. Native empty message reads **No messages yet**. H supplies populated fixture messages and a fallback previous fixture only.

M builds earlier chronological labels plus an anchor if the previously-latest message changed; when a request is present, includes nonempty latest before the card. G appends current latest to window history; no anchor preservation. Both are selectable native formatted text, and the main list owns vertical scrolling. macOS wide tables have a separate horizontal scroller. H uses explicit prewritten HTML (headings, links, lists, code); it has no backend parser or arbitrary-message ingestion.

Markdown native common source: [parser](../../../src/domain/markdown.rs) `parse`. Supports emphasis,strong,strike,headings,ordered/unordered/task lists,quotes,inline/fenced code,hard breaks and rule text. Soft breaks become spaces. Raw HTML is literal text, not executed. Images are not fetched. Links are only HTTP, HTTPS or mailto; local/command URLs stay text. GFM pipe tables are enabled. The parser preserves table/row/column identity, header state, alignment and inline styles; text-only projections use visible cell separators and row breaks. On macOS, table columns are measured from their unwrapped cell text using the displayed fonts and padding. The table fills at least its message viewport; its document width is the measured content width capped at twice that viewport. Overflow enables a native horizontal scroller; text beyond the cap wraps within its column. Vertical gestures over a table continue scrolling the session list; horizontal gestures and Shift-wheel scroll the table. Each table scrolls independently, without widening adjacent prose. Rebuilding a message (including host width changes) resets that table's horizontal offset. GNOME retains its text projection; this macOS addition does not claim GNOME parity. There is no native syntax highlighter. M uses attributed NSTextField for ordinary messages and a read-only selectable TextKit1 NSTextView per table, with ordinary-width attributed labels for surrounding prose; G renders Pango markup. G preserves textual list/quote projection but does not reproduce M's paragraph indentation; exact typography is platform-specific.


Sources: [M markdown](../../../src/macos/markdown.rs) `message`, `attributed`; [G model](../../../src/linux/model.rs) `markup`; [G widgets](../../../src/linux/widgets.rs) `message`; [H CSS/fixtures](../../../design/previews/monitor-ui.html) `.aam-message`, `sessionMarkup`.

## Embedded agent images

M displays already-published PNG/JPEG tool images under their message using native NSImageView; no URL fetching or transcript reads occur in the frontend. This applies to current output, previous messages, and the saved latest-message anchor. An image-only `[Image]` placeholder is hidden only when a preview was successfully created. Invalid/unsupported images retain the text fallback. Text accompanying images remains selectable. Images preserve their aspect ratio, fit the message width and a maximum height of240pt, and are never enlarged beyond their pixel dimensions; stacked previews have8pt gaps. They scroll with the session content and have no separate keyboard target or image-opening action. Before decoding, reject unknown/zero dimensions, dimensions above8192, and a cumulative pixel budget above16 million per message; inspect at most10 images. WebP currently has no dimension reader and therefore falls back to text in this surface. G/H have no equivalent live-image rendering contract; Telegram forwarding is independent. <a id="sessions-progress"></a>
## Current work caption

M/H show a muted, selectable single-line caption with tail ellipsis after the latest message and before metadata while a session is Working and has no active request. It is ephemeral activity, not a history message or approval. M uses11pt tertiary text, a16pt label,8pt preceding gap and the full caption as tooltip. Finishing an individual command/tool does not erase the last caption while the agent remains Working. A new nonempty activity description replaces it; empty reasoning summaries retain the previous caption. A subsequent agent message clears that old detail. The adapter's explicit current-action marker governs this caption, rather than its position relative to transcript messages in the merged timestamp-sorted activity list. A command first observed while waiting for approval can retain an earlier start time and still be the current command after Allow; its caption must remain visible. A source message that supersedes the action clears the marker. Idle/disconnection removes the line; a human request hides it until work resumes. Do not turn a status flag into a request card or request notification.

Codex owner snapshots/patches supply current command/tool metadata and public reasoning summaries; terminal App Server `item/started`, `item/completed` and public `item/reasoning/summaryTextDelta` notifications provide equivalent captions. Render known in-progress commands as **Running <command>**, tools as **Running <tool>…**, file changes as **Editing files…**, web searches as **Searching the web…**, and available public summaries as **Thinking: <summary>**. No arbitrary transcript reasoning content, encrypted reasoning, tool arguments/output, image data or full conversation history is included. While Working, missing/blank detail displays **Working…** instead of hiding the status line and shimmer; a known reasoning item with an empty public summary displays **Thinking…**. No details are inferred from private reasoning or tool output; joining an already-running terminal thread does not request its history merely to obtain a caption. Both Codex transports can show **Thinking…** before public summary text arrives. G and Telegram do not currently present this caption.

Descriptions are capped at512 Unicode characters; owner projection retains progress metadata only when its encoded field is at most8192 bytes, using the existing bounded streaming/spill decoder for oversized values. Public summary deltas are bounded separately and apply only to the current item. The last caption from the current turn can remain after its tool completes; it describes the last displayed activity, not a still-running process. A new turn/message must never resurrect an older caption. Captions never enable a human response control or cause a new request notification. Source: [Codex progress](../../../src/agents/codex/progress.rs) `current`, `caption`; [owner projection](../../../src/agents/codex/projection.rs) `Shape::Brief`; [App Server](../../../src/agents/codex/app_server.rs) `Connection::event`; [M menu](../../../src/macos/menu.rs) `render_rows`; [H](../../../src/web/monitor.js) `progressMarkup`.

H additionally previews a green highlight clipped to the work-caption text. It travels left to right during the first83.333% of a6-second cycle (5 seconds), followed by a1-second pause, then rests outside the text until the next cycle. A synchronized, non-interactive and accessibility-hidden text layer adds a2px blur and4px green glow only around the moving highlight. Base text stays muted between passes. Light/dark greens differ for contrast. The reduced-motion preference and the prototype's animation toggle disable the sweep. M uses the same5-second sweep /1-second pause and ease-in-out timing through a click-through native overlay. Its green glyphs and4pt halo are rasterized once per view/appearance; a moving alpha band samples that cached raster at at most30 updates per second while the popup is open. Pause frames and Reduce Motion do not animate. Closing the popup releases the cached halo. Native text remains selectable and is the sole accessibility text; the decorative overlay has no focus or pointer target. The native Menu bar animation setting retains its existing scope; system Reduce Motion disables this popup effect. Source: [native caption](../../../src/macos/work_caption.rs) `WorkGlow`, `position`.

## Session message composer

M/H append an automatically growing multiline **Message agent…** field with an inset, icon-only **Send message** button after the latest message and before session metadata. Show it only in expanded Idle sessions (including unseen completions); hide it for Working, Confirmation, Unknown, or any active approval/question. A draft survives collapse, filtering, popup close, and temporary work/request states during this process; session removal discards it. Drafts are not persisted to disk. M retains the native field/controller across row rebuilds and restores the editing selection after layout. H retains drafts across snapshot replacements and simulates delivery through its mock host. G has no corresponding composer yet.

M requires the explicit `can_send_message` capability to enable input. Otherwise the disabled field displays a note directing the user to the agent app. Codex direct owner IPC and existing shared App Server terminal connections advertise this capability; Claude/Cline do not. Terminal sends revalidate loaded/idle state and submit to the same thread without configuration overrides or resuming an unloaded thread. Availability can change before submission, in which case the transport reports failure. M shows delivery failures beneath the field, with the full error in a tooltip, and preserves the draft. It does not open the host or install a new connection as a fallback.

**SE-08 (M implemented; H simulated; G missing):** Shift-Return inserts a newline; Return or Send submits the current text once through the shared monitor message command, addressed to this session's stable key. Whitespace-only input and text above16000 Unicode characters must not dispatch. Disable input and Send while a delivery is pending; show **Sending…**. Clear the draft only on confirmed successful delivery. On failure, retain the draft and re-enable explicit retry if the session is still idle/live. Never automatically retry. Recheck session availability against the current snapshot immediately before dispatch. Working/request transitions hide the composer without discarding its draft. No success toast or popup dismissal is required.

Input accepts native editing shortcuts, including Command-V; Left/Right edit text and must not toggle session disclosure. Up/Down leave editing and move through the popup's existing ordered targets. The input is one target, followed by enabled Send; blank drafts omit disabled Send from navigation. Focusing the input starts editing directly. Input has a rounded resting fill with only the theme keyboard outline while focused, without a hover fill. Send uses the shared glass hover/focus surface. The input grows vertically to fit soft-wrapped and explicitly separated lines, shrinks when text is removed or successfully sent, and retains its selection and draft through resizing. The session metadata moves below it; popup overflow uses the existing document scroll. The empty field has a 32 pt/px fill and no Send control. A nonblank single line uses a 44 pt/px fill when the measured text fits before the right-side button (10 pt left padding, 48 pt reserved at the right in H; equivalent native text-cell clearance in M). Its 28×28 round upward-arrow button is vertically centered. A soft-wrapped line, explicit newline, or text reaching the button area switches to a full-width text region with 10 pt top padding and a 44 pt/px bottom reservation; Send sits 8 pt/px from the lower-right inside edge. Clearing the draft returns to the compact empty state. Native drawing adds 4 pt of transparent clearance around the fill; feedback reserves 16 pt only when nonempty, with 10 pt text. H measures browser text and scroll height; M measures the native field cell at 12 pt. A disconnected/native pending field retains the same geometry and draft. The composer is placed8pt below the message, before metadata and scrolls with session content, above the quota overlay's reserved trailing clearance.

Sources: [M composer](../../../src/macos/session_composer.rs) `Composer`, `available`; [M menu](../../../src/macos/menu.rs) `render_rows`, `handle_session_key`, `keyboard_targets`; [shared delivery](../../../src/actors/monitor/mod.rs) `Command::SendMessage`, `Command::MessageSent`; [H](../../../src/web/monitor.js) `composerMarkup`, submit handler; [mock host](../../../design/previews/mock-data.js) `message` handler.

### Markdown table presentation (macOS)

Pipe tables require a valid Markdown header separator row. macOS renders them using native NSTextTable/NSTextTableBlock paragraphs in a transparent, non-editable, selectable NSTextView. Header cells are bold with a subtle background; cells have0.5pt separators and5pt padding. Column widths use bounded relative content-length weights (8–40 characters per column) within the message width; long content wraps inside cells and contributes to measured message height. Left/center/right alignment follows the Markdown colon markers, with left as the default. Inline strong/emphasis/code and safe links retain their existing styles. Empty cells retain their geometry; literal fenced code and malformed pipe text remain ordinary text. Separate tables have distinct identities. The same renderer is used for current messages, earlier history and approval descriptions; the main list remains the scrolling region. There is no WebKit or remote asset loading. Ordinary messages retain the existing NSTextField presentation.

GNOME and Telegram currently consume the shared text projection with cell separators and row breaks; they do not gain a graphical table grid from this change. The HTML prototype accepts prepared fixture HTML and has no new Markdown parser. These are presentation differences, not verified grid parity. Sources: `domain/markdown.rs` `TableCell`, `parse`; `macos/markdown.rs` `message`, `attributed`; `MenuController::render_rows`. Coverage: parser cases for alignment/inline formatting/empty cells/escaped pipes/multiple tables/malformed code; offscreen native captures in both appearances and narrow-width wrapping assertions.

No frontend may treat equal displayed texts as event identity. Multiple same-kind messages/actions can coexist in the bounded tail. Current native layouts project the latest agent output and oldest pending request; earlier output remains accessible through existing source-history paging. A completed command caption may stay current until a newer description/message/turn supersedes it; its execution status and caption eligibility are independent. Message sending requires the explicit connection capability, not merely a visible transcript or request observation.

Working-status simplification (2026-11-17, M/H/live web): the right-side green filled Play badge is omitted for working sessions. The working robot's green illumination/eye animation, current-action caption and aggregate counters remain unchanged. Request and unseen-finished badges keep their established positions and behavior, as does the disclosure chevron. Sources: `MenuController::status_icon`, `src/web/monitor.js::status`. This supersedes the earlier Play-badge rendering descriptions.

Flat-list revision (2026-11-17): macOS renders every session in the same list with uniform separators, including at application transitions.
