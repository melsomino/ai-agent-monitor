# Personal Telegram bot UX

<a id="tg-scope"></a>
## Channel and prerequisites

Telegram is the same shared Rust human-interactor implementation on M/G; frontend differences concern setup/native link opening/credential storage. H has no Telegram surface. Bot API calls go directly from resident computer to Telegram over HTTPS; no monitor relay backend. Computer awake, network available, monitor running are required. Telegram UI controls alignment, native app notifications and message appearance; inline keyboards are centered by Telegram, with no left-alignment setting in this implementation.

Source: [actor](../../../src/actors/human/telegram.rs) `Worker`, `Pending`; [browser](../../../src/actors/human/telegram/sessions.rs) `Browser`; [formatted text](../../../src/actors/human/telegram/text.rs) `Text`; [settings](../components/settings.md#settings-telegram).

<a id="tg-setup"></a>
## Setup, pairing and replacement state machine

**TG-01 (S/T):** Only the paired private account can answer, browse and send to sessions. A valid bot token alone is not a complete connection. Connect validates format (≤256bytes,numeric ID colon ≥20allowed secret characters), getMe identity and no existing webhook. Bot must be dedicated: another poller/webhook can conflict.

Initial Connect saves token to credential store, resets new config, creates random128-bit `/start` payload valid600seconds and opens bot link once through native setup. Press Start with exact unexpired payload from positive user ID equal chat ID and `chat.type=private` pairs/enables. Group chats and wrong/expired payload ignored. Existing user may be recognized from valid configuration; new token generally still requires activation. Expired setup status asks reconnect; no old nonce can authorize. Setup and connected management are in one native settings window, never a browser-hosted configuration form.

Change bot enters setting_up without disconnecting old token/user. Candidate token separately polled,600sdeadline, replacement pairing constrained to existing private owner. New network/keyring/config failure retains old connection; Cancel drops candidate and resumes old presentation. Successful install commits candidate token/config, retires old request messages, announces bot change, resets commands/poll generation, sends Connected greeting. Old poll completions ignored by generation. Credential persistence attempts rollback if new config save fails.

Unlink: retire remote active controls; delete credential/config; clear pairing/outbox/token. If credential deletion fails, disable notifications and report error rather than claiming clean unlink. Cancel differs initially M/G as listed in [settings](../components/settings.md#settings-telegram). Commands available while notifications disabled if already paired; response authorization additionally requires enabled.

<a id="tg-navigation"></a>
## Commands and session browser

Persistent reply keyboard: **Sessions**, **Help**, captions without slash. Bot command menu registers sessions/web_access/info/help; `/status` is accepted but not registered as a visible menu item. `/start` after pairing acts Help. Recognizes `/command@bot_username` case-insensitive target; wrong bot ignored. Text “Sessions”,“Status”,“Info”,“Help” is command only outside explicit reply (slash commands take precedence even inside reply). No Refresh buttons; legacy refresh callback recognized but not generated.

`/web_access` (alias `/web`; no reply-keyboard button) requests a fresh browser pairing code over authenticated local IPC and sends the combined `pairingLinks` list: connected Cloudflare/ngrok/Tuna origins, local interface addresses and loopback, each with its address-kind label. The command does not start the listener or a tunnel. When off, it replies **Web access is off. Enable it in AI Agent Monitor → Settings → Web, then use Web access again.** It preserves the selected session and works for the paired private-chat owner even while notification delivery is paused. The links share one single-use code, expire after two minutes and contain the code in the URL fragment. Creating them renews the QR pairing code but does not revoke established browsers. Long lists are split into bounded command replies; link previews are disabled on command responses. Local addresses require a reachable network; loopback is labeled for the monitor host only. Transport/IPC failures follow the existing command-error reply path. No provider credentials are sent. Sources: `Worker::command`, `web_access_links_with`, `bot_command`, `command_keyboard`, `Worker::ensure_commands`; web pairing contract: [Web access](../../web-access.md).

`/sessions`: new bounded browser, retires previous browser message, clears selected session and persists selection. Header Sessions(n), Select a session to expand it; pagination30per page, Previous/Next. Empty No open agent sessions. Filter applications, group ordering by native host platform natural collator, no group-heading buttons. Each session is one inline keyboard row: host emoji, normalized/truncated title (64 UTF-16 budget), status orange/green, right chevron. No blue completion marker in bot. Host emoji VSCode💻,Terminal⌨️,Codex desktop🤖,other🖥,Unknown◻️. Button captions bounded79/80units. Native app icons cannot be embedded as images inside Telegram inline-button text by this implementation.

Click title row selects that stable session ID, resets detail/history state. Changes in sort order do not retarget old key indices. Session view header **emoji + bold title + optional status**; no written VS Code subtitle, no type-a-message guidance, no success Message sent line. Latest Markdown below, then a navigation keyboard. Request bodies, commands and answer buttons are never embedded in this card. Previous message row, optional Latest message, then ‹ Sessions and Info. Info replaces body with folder `~`-shortened path and optional branch; ‹ Message returns. A closed/hidden selected session shows **This session is closed or hidden in Applications settings.** with navigation; plain-text sends then fail against monitor if unavailable. Pagination/back clears selection. Selection is persisted separately from last rendered browser card, so unrelated requests do not steal chat destination.

**TG-02 (S/T):** Ordinary nonblank chat text while a session is selected MUST send to that selected agent session, even after another session's request arrives/is answered. Explicit Reply to a pending request instead addresses custom answer. A stale/unmatched explicit reply does not fall through to a new agent chat message. No session → instruct choose in Sessions. Send identity is telegram:chat:messageID, validated centrally; not shell execution.

<a id="tg-messages"></a>
## Automatic updates and history

**TG-03 (S/T):** Status changes edit the **current session card** rather than delete/recreate it. A pending request may change its header status marker, but its body and answer controls belong exclusively to a separate message. New agent text (same selected session, changed nonempty latest) first removes old message's inline keyboard, then posts a new message with current controls. Old history text remains without active controls. New status alone does not append duplicate agent text. On failure to strip old controls, do not advance; retry. Session navigation and card replacement never change the authority of separate request messages.

Current browser stores last rendered payload; unchanged content makes no API edit. Successful card send/edit commits displayed agent content only; it cannot mark a request delivered or suppress its notification. New latest resets info/earlier view, preserves outgoing send tracking. Browser session output limited1700units, whole text3900; truncation adds ellipsis and clips entities. There is no document attachment for full overflow.

Previous message requests Telegram-specific history generation; display one selected earlier message with Earlier message label, not all accumulated history. Repeated Previous moves cursor earlier; Latest resets. Loading… caption while awaiting,10s interrupted note, no earlier messages exhaustion. Returning to Sessions resets detail. History unavailable/error shown in body. Local popup history unaffected.

<a id="tg-images"></a>
## Codex image delivery

**TG-IMAGE-01 (implemented):** In a selected session's message view, embedded images emitted by Codex tool outputs are sent as separate Telegram media messages, followed by a fresh text card with the current navigation controls. A successfully delivered image causes the old text card's keyboard to be retired before posting the new text card. Media captions identify the session; image messages have no answer keyboard. Reading Previous message similarly exposes embedded images from that history page. Returning to Latest restores the current-turn media selection.

Supported source: `response_item` with `function_call_output` or `custom_tool_call_output`; output is either a content-block array or a JSON-encoded array. Image blocks can be `input_image`, `output_image` or `image`, but only in tool outputs (the name `input_image` in a tool response does not make it a user's upload). Accept embedded base64 PNG/JPEG/WebP with matching file signatures. User messages/attachments, remote URLs, arbitrary local file references and images nested in compaction mirrors are excluded. Claude/Cline media extraction is not implemented.

PNG/JPEG with known dimensions satisfying Telegram photo constraints are uploaded via `sendPhoto`; unknown dimensions, WebP, oversized dimensions/extreme aspect ratios or images above10,000,000 bytes use `sendDocument`. Uploads use the original decoded bytes. Limits:10MiB per image,10 images and20MiB per output/current turn. Encoded records above24MiB are skipped. Latest discovery initially inspects at most the final32MiB of each open rollout, then reads complete appended records incrementally, retaining shared image buffers without reparsing unchanged payloads. A new user message/turn clears current images; missing/truncated/replaced transcripts reset discovery. Earlier supported images remain available on demand through history, subject to per-record limits.

**TG-IMAGE-02:** Updates must not resend identical image bytes repeatedly. A browser tracks at most512 successful `(session key, image ID)` deliveries; identity is a stable content fingerprint, not a temporary pathname. Identical images repeated inside one output/current turn are deduplicated. The delivery ledger belongs to the current browser lifetime, so a fresh Sessions browser/monitor restart can display media again. Unsupported/corrupt blocks are skipped rather than fetched from external locations. Normal photo failures are retried no sooner than15 seconds later; the text/approval card can still update and retain valid answers. Only an API success with a message ID marks an image delivered. Ambiguous network failures can still cause a duplicate on retry; Telegram uploads have no application idempotency key.

**TG-IMAGE-03:** The agent adapter publishes bounded image buffers in monitor state. Telegram reads only that state and selected history pages; it does not open agent transcripts itself. Decoding happens in the adapter/history reader. Private temporary upload files are removed after the request; bot tokens remain in curl stdin, not arguments/logs. Session visibility filters apply before choosing media. Native notification bodies remain text-only; native windows currently show the history placeholder `[Image]` rather than image thumbnails. History retains at most40MiB of media per consumer, preferring the most recently requested pages; text/cursors remain usable when older page media is discarded.

Sources: [domain media](../../../src/domain/media.rs) `Image`, [Codex images](../../../src/agents/codex/images.rs) `output_images`, `Cache::latest`, [history](../../../src/agents/history.rs) `codex`, `jsonl`, [Telegram browser](../../../src/actors/human/telegram/sessions.rs) `pending_image`, `image_sent`, `content`, [worker](../../../src/actors/human/telegram.rs) `flush_browser_media_with`, `send_image`, `image_method`.

Acceptance: select a session with a new output image; observe one media upload and a last text card with navigation buttons. Refresh several times without duplicate uploads; change status/approval without resending media. Load an older image page with Previous. Verify a user's screenshot is excluded, hidden sessions cannot send images, and malformed base64/external paths are not fetched. Simulate upload failure and answer a pending question through its independent request message. Test large/partial transcript records, a new turn and truncation. Automated transport tests use a fake sender; delivery to a live Telegram bot still requires a manual check after the updated app is launched.

<a id="tg-requests"></a>
## Requests, questions and deduplication

Pending standalone message starts bold session title then newline/body, **no agent-name line or blank line after title**. Uses Markdown projection, literal preformatted command, optional action-detail code block near action caption, one inline answer button per row. Command bounded1600units,bash language; action detail300units,bash only Allow similar commands. Approval body2200; choice description300. Wire JSON decisions not displayed as raw button captions.

Structured questions delivered sequentially: Question i of n, current title, choices + optional descriptions; freeform instructs Reply to this message. Up to90choices/actions rendered. Preset picks value; custom trim/nonblank≤4096characters and only if freeform. Each intermediate choice advances question and rotates nonce; no partial monitor send. Complete set validated and sent once. Secret current question shows private-answer instruction, no body/choices/secret answer controls; may still retain separately rendered latest agent message in browser. No general promise of redacting unrelated sensitive content.

**TG-04 (S/T):** Every request owns one separate Telegram message, regardless of which session is selected or whether its card is visible. First delivery uses sendMessage with notifications enabled, a bold session title, the full bounded request body/command, and the request's answer keyboard. Mark delivered only when Telegram returns a message ID; errors or missing IDs leave it queued. Browsing or editing a session card MUST NOT suppress, adopt, retire or gain answer authority over this message. No additional short alert is sent.

Status changes and intermediate questions edit that same request message. Intermediate answers rotate the nonce, queue an edit with retry and do not submit partial answers to the monitor. Custom answers require an explicit Reply to the request message. Answer callbacks require its message ID and current nonce; callbacks copied to a session card are rejected. A new request gets its own message; ordinary phase updates do not send another one. Resolution/removal retires only the request message through delete/fallback cleanup. The selected session and its content card remain intact.

Telegram/device notification settings still govern actual push display. An ambiguous transport failure after Telegram accepted a send can produce a duplicate on retry because Bot API sendMessage has no application idempotency key.

Pending delivery capped128requests, command outbox128. New questions take priority; paced1second between successful work,15second retry for transport/cleanup/edits. Polling separately from outgoing updates (loop50ms); a long incoming poll must not block notification delivery. Shutdown/restart retires persisted active message IDs; old callback authority is not reconstructed from IDs. Cleanup/delete already-not-found and edit-not-modified treated success. Offline removal remains queued for retry, so visible old Telegram text may persist while response authority is gone.

<a id="tg-errors"></a>
## Answer validation and error presentation

Validate paired sender/chat/private type; message ID; current request nonce and allowed index; current approval equality, interaction equality, authoritative session, not already Sending/Reconciling; then submit via monitor. Central monitor additionally validates expiry. Changed same-ID interaction is **not** automatically replaced in `sync_sessions` (it only adds absent keys); stale pending can remain and answer reports **The question changed. Answer it in the agent app.** This differs from native rebinding; [D-10](../discrepancies.md#d-10).

Sending removes answer keyboard + appends Sending answer…; Reconciling removes it + Checking whether the agent received the answer…; Failed includes error and can retain choices. Callback feedback is small Telegram toast (Updated., Answer queued., unavailable/account error), not a new persistent success message. Chat sends show Sending message… while in flight, no Sent line after success; failure appended to session body.

Transport errors are short status notes: cannot reach Telegram/check connection;401token rejected;409another client/webhook;429rate limit retry;403unblock bot; generic incomplete request. No automatic permission retry from uncertain delivery. Test sends one harmless connection message; API failure note shown in settings. Private-token input and command payloads kept out of logs/argv; format examples in documentation are not real credentials.

<a id="tg-acceptance"></a>
## Acceptance

Pair only correct private account; wrong nonce/group/user ignored. Cancel a staged replacement on network/keyring failure and confirm old bot works. Open session A, receive and answer B, send plain text: A remains destination. Reply to B explicitly: answer B, no plain message to A. Exercise sequential two questions including no-custom/secret. Submit externally and verify separate request retirement without removing the session card. Verify a session card contains no request body, command or response buttons, and cannot receive a request answer. A failed card edit must not block independent request delivery. Change only status: current ID stays; change latest text: old buttons removed then one new message. Offline transport must not fabricate delivery, steal selection, or send an answer twice. Compare Markdown entities with emoji/Unicode, long command truncation and safe links.
