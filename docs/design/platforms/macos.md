# macOS AppKit supplement

The [2026-11-07 glass surface revision](../components/glass-surfaces.md) describes the current AppKit monitor layout, gradient drawing and remaining prototype differences. It supersedes older neutral surface colors and monitor geometry in this supplement.

<a id="macos-shell"></a>
## Native shell contract (S/P; runtime outcome U where noted)

Resident is an accessory NSApplication, no normal Dock/task-switcher app window for the session popup. NSStatusItem owns an attached NSMenu; menu view is a custom enabled item, autoenable off. Native menu tracking owns opening/dismissal/selected menu-bar background in pinned mode. `performClick` opens it; `cancelTracking` dismisses. The user can explicitly detach this content into a standard window as specified below. Native horizontal navigation passes through only when no session target owns Left/Right in the menu. Whether other apps' menu extras participate and exactly when selection clears remains an OS-runtime check.

<a id="macos-detached-window"></a>
### Detaching and pinning the monitor

The pin button occupies a 28×28-point circular target in the upper-left corner of the window content. The complete hover is inset 1 point from the top and left content edges when the list is at the top. It is a root overlay independent of the list’s 11-point horizontal gutter; its vertical position follows the header’s scroll offset and it becomes hidden once scrolled offscreen. Its tooltip/accessibility description is **Detach window**. It scrolls with the header rather than occupying an independent fixed bar. Clicking it ends native menu tracking, then reparents the existing root view into one titled NSWindow. It MUST preserve session disclosures, drafts, question choices and scroll position, allowing device-pixel rounding and viewport clamping. It MUST NOT create another monitor tree. The monitoring actor and connections are unchanged.

The detached window has the standard macOS title, traffic lights, movement, minimization, zoom and resize controls. Its content minimum is 460×200 points. The operating system supplies corner rounding and title-bar decoration; the content draws neither a separate rounded panel nor NSMenu padding extensions. Menu work-area anchoring and custom side-only resize/cursor handling do not apply to this host. Native resizing changes the viewport; changing width reflows session content. Live content updates MUST NOT reset the user's chosen window height or reposition the window.

While a detached window exists, the app uses the Regular activation policy: it participates in Dock and the macOS Cmd+Tab application switcher, including while minimized. Pinning or closing that window restores Accessory policy and removes those entries; the status item remains available in both modes. This is an application-level switcher entry; third-party window switchers retain their own filtering rules. Source: `MenuController::set_detached_application_policy`. Hidden verification retains Prohibited policy and does not exercise actual Dock/switcher presentation.

The scrolling header's detach button is hidden while detached. A native left title-bar accessory displays `pin.fill` with **Pin to menu bar** tooltip/accessibility description. Clicking it moves the same root back into the status menu and opens that menu. The existing focus target is retained rather than automatically focusing the first answer again. The standalone window is closed without treating that transition as a user close. Pin/detach mode is not persisted across launches.

Pinned width and standalone geometry MUST be independent. `MonitorWindowWidth` remains the pinned menu's width preference. Detaching remembers that width; pinning restores it regardless of standalone resizing. The standalone frame (position and size) is saved with the native frame name `MonitorDetachedWindow` on movement, resize and close, and restored on subsequent detachment, including after relaunch. Changing the pinned width MUST NOT overwrite this frame. Native screen constraints may adjust a restored frame when displays change. With no saved standalone frame, the first detachment starts from the popup's current geometry. Neither preference changes the initial pinned mode after launch.

Clicking the status item or invoking the global monitor shortcut while detached brings the existing window forward and restores it if minimized; no second window or popup is created. Opening an agent application or GitHub does not close the detached window. Its keyboard navigation operates only while it is the key window. Cmd+W or the native close button closes the standalone UI; monitoring/status counters continue. Closing releases the view controller and its tracking timers, preserving text drafts in the resident controller; the next status-item opening creates a fresh pinned menu. Inline settings remain inside whichever host currently owns the content.

Sources: `src/macos/menu.rs`: `toggle_pin`, `detach_window`, `reattach_window`, `dispose_detached`, `layout_detached`, `focus_detached`, NSMenuDelegate and NSWindowDelegate implementations. `src/macos/menu_visual_test.rs` exercises host identity, scroll/draft preservation, resizing, reattachment and native close in hidden AppKit windows. Native title-bar appearance, real menu tracking transitions, minimize/zoom and multiple-display placement still require interactive verification.

AppKit material is retained; a click-through MeshView samples the continuous scrolling scene over the complete popup, with dynamic appearance and matching slices over top/bottom OS padding. Correct before `viewWillDraw` and frame updates, rather than visible post-open jump. Work-area clamping and max-height described in [lifecycle](../interactions/input-lifecycle.md#life-open); OS corners/shadow not hardcoded to prototype18px.

<a id="macos-popup-width"></a>
The popup can be resized horizontally by dragging either vertical edge (6-point hit area, horizontal resize cursor), excluding the top and bottom 18-point corner zones. The top/bottom edges and all corners do not start resizing. While the interactive menu is open, the monitor explicitly activates its accessory app so NSCursor updates affect the visible system cursor, rather than only this process's inactive cursor. The app active before opening is retained and reactivated on close only if the monitor still owns the foreground and that app is still running. An explicit user switch to another application is preserved. This activation also covers inline settings. There is no separate cursor window or tracking overlay; the existing menu pointer poll and event dispatch set the horizontal cursor on the same real-window edge strips used for resize input, including the native padding. Closing the menu releases the owned cursor before restoring the previous app. The controller keeps the custom item and actual tracking window at the same chosen width after native menu updates and before drawing. NSMenu can retain its previous wider measurement when an item shrinks; that cached menu size is not added as padding to subsequent drags. The drag handler anchors the opposite edge where screen bounds permit. Header icons and their hover backgrounds share the same horizontal anchoring. The default/minimum width is 460 points; the maximum is the current screen's visible width minus 8 points. Messages, Markdown tables, request cards, question forms and composers reflow at the chosen width; status/disclosure controls and header actions remain right-aligned. Resizing preserves custom answer selections, text drafts and native text selection. The chosen width is saved on drag release in the macOS preference `MonitorWindowWidth`, restored on the next launch and clamped to the available screen. The floating quota capsules remain centered and never exceed their default 428-point width (the 460-point quota group including its side insets), even when the host expands. Height continues to follow content subject to the existing work-area limit. Retained settings panes keep their established 460-point form width within the wider host; the complete settings surface, including header, tabs and pane, is centered horizontally. Its scroll document spans the host width, so no horizontal scrollbar is introduced. This is a macOS host feature; it does not establish a resize gesture for mobile browsers or GNOME.

Acceptance: drag each edge wider and narrower with a multi-line draft and an unanswered question; verify reflow, unchanged draft/selection and no request submission; close/reopen and relaunch to verify width retention; move to a narrower screen to check clamping. Native menu tracking/cursor behavior requires runtime verification; renderer fixtures cover reflow and input preservation.

Scroll elasticity remains disabled. Application headings scroll with the document and are repositioned from their first session after disclosure layout changes. Reveal clip is not an inner scroller; outer list routes wheel. Main-thread pointer polling in common run-loop modes handles non-first-responder hover, button clipping and editing focus. Inline input uses field editor plus custom focus/caret decoration because menu tracking may not make its window key. This is not a recommended mechanism for future platforms—only the visible single-focus/editing result is shared.

Sources: [native](../../../src/macos/native.rs) `run`, `MonitorApplication`, `NotificationDelegate`; [menu](../../../src/macos/menu.rs) `build_status_item`, `build_menu`, `PanelView`, `sync_backdrop`, `OverlayView`, `close_panel`, `handle_session_key`; [pointer](../../../src/macos/pointer.rs); [hotkey](../../../src/macos/hotkey.rs); [inline fields](../../../src/macos/inline_questions.rs).

Enabled clickable surfaces use the pointing-hand cursor, including session title targets, disclosure/status buttons, approval/answer actions and inline settings controls. Disabled controls and empty space do not use it. Native text editors and selectable message content retain their native cursor behavior. The horizontal resize cursor takes priority at pinned-window edges. The existing visible-window pointer sampler updates the hand without another timer and releases only its own cursor on exit/close; it does not set cursors over another window. Sources: `MenuController::sync_action_cursor`, `action_cursor_at`, `paint_hand_cursor`.

While the left mouse button is held, snapshot-driven popup/settings reconstruction, composer remeasurement, disclosure advancement and automatic answer focus are deferred so the native pressed control remains attached through mouse tracking. Pending revisions are not consumed; the first update after release applies the latest snapshot and coalesces intermediate revisions. Resident status counters, monitoring and notification delivery continue. Explicit actions still validate the live request through the monitor when submitted. Sources: `MenuController::mouse_tracking_active`, `receive_sessions_with_mouse`, `poll_state`, `poll_pointer`; hidden AppKit regression publishes three revisions during a simulated held click and verifies row identity, resident updates and latest-state application after release.

<a id="macos-navigation"></a>
## Host navigation and permission prompts

VS Code target uses pinned workspace association, not latest tool cwd. M `open_target` first delegates terminal custom targets; otherwise it requires a parsable VS Code path. For a missing project path, it activates running VS Code or opens the VS Code application rather than requesting the missing path. For an existing path it opens the URI through NSWorkspace. A generic “activate the named Desktop client” route is not implemented here; Codex desktop sessions also receive the adapter's project/editor target. Terminal target encodes agent/session/cwd rather than interpolating commands. Terminal host resolved through live process ancestry/TTY; resume/session identity preferred to cwd, ambiguous same-directory sessions not guessed.

Terminal.app AppleScript selects matching tab by TTY and activates window; iTerm finds matching session/tab. Warp/other hosts without tab script focus application only, not guaranteed tab. Automation permission may be needed; no custom permission bypass/settings control. A process retained only by daemon rollout must not keep a closed terminal session visible. Navigation no-ops/ambiguous fallbacks can occur; source does not guarantee every terminal vendor opens exact tab.

Sources: [terminal](../../../src/macos/terminal.rs) `target`, `retain_live_codex`, `choose`, `focus`, `TERMINAL_SCRIPT`, `ITERM_SCRIPT`; [native](../../../src/macos/native.rs) `open_target`; [Codex VSCode](../../../src/agents/codex/vscode.rs).

## Settings, notifications, accessibility and system controls

Settings is an inline scrollable screen within the existing NSMenu host, with retained native panes, Sessions/Escape return and no separate settings window. See [settings shell](../components/settings.md#settings-shell) for geometry, focus and lifecycle. General uses native checkboxes; Applications native switches. Shortcut uses Carbon registration while menu closed, native menu key equivalent while open. Launch at login uses SMAppService, can require separate approval in macOS settings.

Notifications use UserNotifications with dynamic request categories; OS policy controls actual banner action density. Notification permission asked after onboarding setup; denial note in Agents. New bundle identity `com.melsomino.ai-agent-monitor` and legacy preference migration exist, but icon cache invalidation is OS-owned and cannot be guaranteed by these source paths.

Accessibility source evidence: SF Symbol accessibility descriptions, button tooltips/labels, title captions, explicit application switch/shortcut-clear labels, system text controls; decorative hitTest None. There is no complete custom NSAccessibility outline/list/expanded-state implementation in these custom rows. Robot/chevron tooltips update; a generic Session details symbol description is not proof of VoiceOver announcement parity. Tab order, VoiceOver navigation, increased contrast, reduced transparency, full keyboard access, IME composition and high zoom require manual verification. Native system colors do not by themselves prove contrast compliance.

Reduced-motion accessibility checked for ambient and session robot eyes; disclosure still animates. Dark/light dynamic provider covers tinted menu, cards, footer, message and hover. No user-facing theme selector in native preferences.

Acceptance supplement: actual side/bottom Dock and offset monitor; popup activation and restoration of the previous app on close, with no restoration over an explicit app switch; native checked background throughout tracking; no header strip during resize; one hover when pointer moves/exits; field caret and cmd+V; automation denied; notification permission/DND; alternate accent/theme. These are not certified by arithmetic/unit tests.

Session robot motion follows [SE-ROBOT-01–03](../components/sessions.md#sessions-robot-motion): the existing popup tracking timer invalidates working robot drawings, sampling a controller-owned monotonic epoch. Reduced motion is read from NSWorkspace. Robot artwork and hit/hover geometry stay fixed; only eye brightness changes.

Application headings are click-through 26-point document views with an unboxed icon/name; the first session reserves26 points above itself. `update_group_headings` uses document coordinates, never viewport pinning. Title destination hints share the title open target and hover/focus lifecycle; hidden hints reserve42 points, protecting status/disclosure controls. See [SE-02/SE-03](../components/sessions.md#sessions-header).

## Visual asset maintenance and renderer verification

[Glass surfaces](../components/glass-surfaces.md#glass-scene) owns current geometry and appearance. Production rendering remains AppKit. `src/macos/visual.rs` draws surfaces, wave, glyphs, progress and thread gradients. `assets/monitor-mesh.png` contains transparent decorative art only, generated from the prototype SVG by `swift scripts/render-monitor-mesh.swift`. WebKit is a development-only asset generator, not a production dependency. Regenerate after changing the prototype mesh geometry/blur.

Run `AAM_VISUAL_PREVIEW_DIR=/tmp/aam-native-visual cargo test --offline --test visual_frontend` to export actual native view-tree PNGs in both appearances. The fixture exercises collapsed/expanded commands, questions, native field editing, working threads, quota, scrolling and all five inline settings tabs, including Web pairing QR, Telegram pane replacement, token editing and keyboard return. It does not start monitor actors or modify preferences. OS window outline, native menu tracking, VoiceOver, IME and increased contrast still require runtime checks.
