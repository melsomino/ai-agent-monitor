# Glass surfaces

<a id="glass-scope"></a>
## Scope and authority

The 2026-11-07 visual revision replaces the earlier neutral surface palette for the HTML prototype and the macOS monitor popup. It does not change request delivery, session state, keyboard traversal, or platform window management. This document supersedes the affected H/M color entries in [visual foundations](foundations.md#visual-colors); the geometry ledger here also supersedes the earlier macOS monitor measurements. GNOME retains the earlier baseline.

H is the visual reference, not proof of production parity. macOS adopts the monitor layout and surface treatment using AppKit drawing and native controls. GNOME has not adopted this revision: it retains its theme-derived neutral popup, request, command, hover and footer surfaces. Settings, notifications, Telegram and the system panel/menu bar retain their existing presentation.

Sources: [prototype styles](../../../src/web/monitor.css), CSS sections `Neon glass concept` and `Layered light`; [AppKit](../../../src/macos/menu.rs), `build_menu`, `sync_backdrop`, `sync_mesh_slice`, `request_action_layout`, `command_text`, `hover_background`, `update_hover`, `request_context`, `render_rows`, `render_footer`; [native drawing](../../../src/macos/visual.rs), `MeshView`, `GlassBox`, `draw_brand_wave`, `UsageTrack`, `QuotaSymbol`, `DecisionIcon`, `draw_thread_line`; [GTK](../../../src/linux/style.css), [GTK tokens](../../../src/linux/style.rs).

<a id="glass-contract"></a>
## Interaction contract

- Decorative surfaces MUST NOT introduce new keyboard targets or change the existing response targets or selection state.
- A command remains selectable, character-wrapped and initially limited to two measured lines in macOS. Its caption-row disclosure remains outside custom keyboard traversal. Surface changes MUST NOT change expansion or submission behavior.
- Hover MUST remain distinct from keyboard focus. macOS supplies its semantic accent fill for the single focused target; the glass decoration adds no reflection to a focused target. Selected radio state remains independent of this fill.
- Both appearances MUST preserve primary text legibility, metadata hierarchy and a command surface darker than its enclosing request surface. Color alone MUST NOT replace the request, working or completion symbols.
- Gradients and reflections are static. They MUST NOT add breathing, pulsing or rotation to controls; existing eye/disclosure animation rules remain in force.

<a id="glass-differences"></a>
## Remaining differences and decisions

macOS now has the scrolling brand header, version/settings/quit controls in that header,14pt session titles,42pt session rows, unboxed application labels, the460pt popup, a decorative wave derived from the prototype's Bézier control points and a quota progress bar. GNOME retains the earlier presentation throughout.

The header is88pt high, in the same scroll document as the sessions. The40×35pt hero robot begins at document x8 (window x19); the brand title begins at x61 (window x72),18pt, with9pt version text to its right. Its11pt summary shows four visible-session counters in this order: **N waiting for you · N working · N finished · N idle**. Waiting includes active requests or Confirmation activity; Working excludes waiting; Finished means Idle with an unseen completion; Idle excludes unseen completions. Amber, green, blue and muted gray-blue distinguish the categories. Categories with zero sessions are omitted, including their separators. Labels are lowercase; when all counts are zero the summary is empty. Unknown activity is not counted as idle and is noted in the summary tooltip. Counters reflect the current application/title filters; there is no total-session/All clear phrase. Settings and Quit retain their existing native actions; the prototype power button only simulates pause. The first group starts after95pt reserved header/inset space. Group heading reserve38pt, later-group gap8pt;24pt app icon and12pt secondary app name align with the robot/title columns. There is no app-group collapse target or heading separator. Subsequent sessions within a group have a muted half-point separator. Expanded detail retains13pt Markdown messages,11pt metadata and its native history/response behavior. Question groups have20pt separation; custom inputs are31pt high and preserve native editing/focus semantics.

OS-owned outer corners, rim and shadow remain native; the prototype's custom gradient outer border is not an exact replica of NSMenu's decoration. AppKit uses the system accent for keyboard selection rather than H's fixed violet. Native font metrics, SF Symbol shapes, text measurement, native field-editor metrics and contextual button wrapping remain platform differences. Native code line height is fixed16pt; H derives15.95px from11×1.45. The native footer renders all reported quota windows, not the prototype's single fixed85% example. Increased contrast/reduced transparency still require runtime review.

The supplied static reference establishes appearance, not hover or pressed-state transitions. Exact reference hover behavior is unknown. Prototype CSS demonstrates one interpretation; it MUST NOT be documented as an observed interaction in the reference image.

<a id="glass-validation"></a>
## Acceptance and evidence

Source inspection establishes the tokens and drawing paths; a successful compile is not visual verification. Review in both Aqua and Dark Aqua:

1. Open a request with command and action-prefix blocks; verify the two-line collapse and expansion, selectable text and continuous rounded border.
2. Move between title, response, radio, input and submit targets. Only the current keyboard target has outlined focus; hovering another control does not change selection or response.
3. Check forms of different heights, empty/long commands, disabled submit and single/multiple-question forms. Decoration must stay behind controls and text.
4. Resize by expanding/collapsing multiple sessions; check the top material extension, footer and native menu edge for flashes or gaps.
5. Check multiple quota windows and no usage: panels must not conceal labels, reset dates, tooltips or utility controls.
6. Compare reduced transparency, increased contrast and alternate accents at runtime. This change has no newly implemented accessibility-specific fallback; compatibility remains unverified.

The HTML prototype was rendered in an offscreen WebKit window and visually inspected. The actual AppKit menu view tree is rendered by [the native visual harness](../../../tests/visual_frontend.rs), using safe fixtures without actors, credentials, screen capture or visible windows. In both Aqua and Dark Aqua it checks nonempty rendering, scene movement on scroll, command disclosure and collapse geometry, exclusion of disclosure from keyboard targets, question rendering and the native input editor. This verifies native view rendering, not the OS-owned NSMenu frame, menu tracking, notification delivery or accessibility system overrides. GNOME adoption remains absent.

## Continuous scene and detail contract

H/M use a continuous document-space mesh behind the header, list and footer. Scrolling moves the mesh with the content; it MUST NOT restart at application groups, request cards or footer. The logical motif is460×1000; alternate mirrored motifs repeat at fixed scale rather than stretching with document height. H applies14px blur and1.08 scale; native uses the corresponding pre-rendered transparent art. Light/dark mesh opacity is.42/.85. A translucent wave at the document top scrolls away with the header. Native menu padding samples the same scene to avoid a separate top strip.

Header controls are tertiary at rest, secondary on hover, primary under native keyboard focus. Request secondary controls have a thin smoky violet rim; primary decisions have a localized upper reflection. Check/cross glyphs are14pt vector strokes alongside captions. Commands have no Copy control; only the caption-row expander remains. Question inputs use a31pt rounded9pt surface, preserving native NSTextField/NSSecureTextField editing and focus; radio artwork is14pt with a5pt selected dot. Field editor and response selection remain separate states.

Expanded session threads use a continuous vertical gradient clipped around marker contours. Request lines start amber, pass through violet and fade completely; working lines start cyan then violet and fade. The gradient must not run through message icons or the terminal dot.

The quota is a single continuous capsule, including its date. There is no inner rounded date divider. Rows have44pt stride; each panel is40pt tall. The18pt hollow chart precedes the label; the8pt track uses #986BFF → #B46DF1 → #DC79ED. Zero/unknown remaining quota leaves an empty track. Percentage and reset-date semantics are unchanged. Its directional rim is cold at upper left, subdued through the middle and pink/violet at lower right.

Header robot detail: the40×35pt artwork uses the prototype SVG head/ear/eye geometry. The compound body and ears share the cyan #A2E4FF → violet #8C75FF gradient (150° CSS direction, violet reached at75%). Cyan #7FE7FF eyes have a4pt soft glow. Ambient halos use3pt #A5B8FF at60% and12pt #6550ED at53%; AppKit reserves24pt transparent overflow around the artwork so shadows are not clipped. This extra paint area is click-through and does not change header alignment or small session-marker geometry.

Session metadata detail: H/M use tertiary text at11px/pt regular weight,12px/pt outline folder/git-branch/cpu artwork,6px/pt icon-to-label gap and18px/pt label origin. Native rows measure15.4pt with2pt inter-row gap, matching H line-height1.4. Without inline question controls the metadata starts12pt after the message/action area. Directory/model tooltips, truncation and selectable native text remain unchanged; native symbols are drawn as matching outline paths rather than using the differently proportioned SF Symbols.

Title hover detail: H/M use a110° CSS-direction blue-violet base (#454C73→#51416C at62% in dark appearance; #BBC9E7→#CEC0EA at52% in light), with cyan light at9%/8% and violet light at96%/100%, both at19% peak opacity. Keyboard focus retains the gradient and adds a2pt theme outline (#7860BC light / #C7B5FF dark) at1pt offset; text retains its normal primary color. Custom fields have no hover fill and focus adds only that outline. Radio artwork has no separate focus outline. ### On-demand reset inventory (2026-11-17, macOS and web)

The first quota capsule has a 24pt/px circular `ellipsis` button immediately after its reset date. Opening it expands the same capsule upwards, with reset inventory above the ordinary quota row. Hover and expanded selection use an opaque solid darker fill (light `#C4B8D6`, dark `#211A2E`), without the gradient glass hover. The icon keeps the ordinary secondary color. No inventory request runs during initial rendering, background quota polling, window opening or snapshot updates. Each collapsed→expanded user action asks the monitor to read inventory; closing never reads/redeems anything. Concurrent reads coalesce into the active request.

While the monitor reports Idle/Loading, show an indeterminate spinner and “Loading usage limit resets…”. Ready shows **Usage limit resets**, a secondary regular “N available” alongside it, and **Expires** at the right in the same primary semibold style as the main heading. Each row shows the provider title and local expiration date/time (or “No expiration”). Count is authoritative even if the returned detail list is shorter. A null detail list is distinct from an empty list: “Expiration details unavailable.” versus “No resets available.” when count is zero. Errors show a bounded inline message; closing/reopening retries. Escape collapses inventory before dismissing the popup. No reset redemption button is implemented.

Native inventory rows use 24pt stride, up to six visible rows with native vertical scrolling for overflow; the complete returned list is retained. A retained NSProgressIndicator animates only during visible loading. The native popup controller owns expansion; the monitor owns request/loading/result/error state. Live web uses the same snapshot state and an authenticated `reset-credits` command. Offline or diagnostic read-only pages disable the button. The prototype simulates a 2.6s request only after the host receives a user request. GNOME does not yet expose this inventory control. Sources: `domain/usage.rs::{Resets,ResetPhase,ResetCredit}`, `actors/monitor/mod.rs`, `agents/codex/usage_resets.rs`, `MenuController::{toggle_usage_resets,render_footer,route_scroll}`, `src/web/monitor.js::renderUsageResets`, `src/web/remote.js`, `src/web/server/{mod,projection}.rs`, `design/previews/mock-data.js`.

Reset disclosure loading contract (2026-11-17): opening MUST synchronously replace any cached rows with the spinner, before the monitor processes the read command. Monitor reset state carries a monotonically increasing request `generation`. A frontend keeps an expected generation until that request is observed; unrelated session revisions containing cached inventory cannot reveal those old rows. A Ready/Error result for the expected generation resolves loading even if the intermediate Loading snapshot was coalesced. Closing clears only local disclosure/loading expectations, not the in-flight read.
