# Settings and setup

<a id="settings-shell"></a>
## Window, navigation, and sizing

M: Settings replaces the session list and quota footer **inside the existing status-menu window**. It creates no separate window and does not activate a normal preferences window. The retained shell has a Sessions back button, Settings title, version, and icon-and-label tabs General (gear), Applications (grid), Agents (robot), Telegram (paper plane), Web (network). Content width460pt; header starts17pt from the top, navigation68pt with81.6×66pt targets and4pt gaps; pane content starts150pt. Header and navigation scroll with the pane. Pane height plus166pt determines the requested popup height, subject to the usual screen/Dock maximum. Overflow uses a transparent nonelastic vertical scroller. Navigation and Sessions use shared glass hover/focus surfaces. Pane action buttons use the same glass action treatment: 12pt medium captions, 12pt corner radius, muted violet fill and fine rim, shared hover and keyboard outline. Disabled actions retain their state and use 45% surface opacity. Native checkboxes and application switches retain their standard artwork. The session-header decorative wave is hidden on the settings screen. The mesh continues through native menu padding at both edges, including below the settings pane.

M Sessions or Escape restores the retained session list, disclosure, drafts and saved scroll offset. Settings keystrokes do not filter session titles or invoke request actions. Tab/Shift-Tab and Up/Down wrap through visible enabled settings controls, including text inputs; Left/Right on a navigation tab selects the adjacent tab. Enter/Space activates the focused nontext control. Text fields use the native field editor, including Command-A/X/C/V; typing and Return remain in the editor. Shortcut recording consumes its own keys. Switching tabs ends recording and commits field editing. Closing the menu exits settings. The last selected tab remains in memory, not on disk. Snapshots continue updating actual controls, including Telegram connected/setup replacement; pane refresh does not replace an unchanged active view or discard its field editor.

G: normal GTK Window560 initial width, toolbar ToolButtons (system/app-grid/custom robot/mail-send symbols), nonhomogeneous Stack of four same-named pages;18page padding,10vertical spacing. Page change/snapshot triggers preferred-height resize, preserves position. Window manager can affect actual decoration/resize behavior. Close hides, retains controls. GNOME still uses a separate settings window.

H: the [in-popup settings prototype](../platforms/html.md#html-inline-settings) uses the same navigation concept with simulated setup states. Sessions/Escape restores list scroll, disclosure, drafts and focus to the gear. Mock animation/application preferences affect fixture rendering; OS setup, shortcuts, credentials and Telegram are not connected to production services. H has responsive wrapping and Home/End tab navigation; M uses fixed native pane geometry. H now matches M/G direct unlink behavior; its replacement/activation states remain simulated.

**SET-02 (H/M):** Opening Settings MUST retain the current session view state and replace its visible content within the same popup. Returning to sessions MUST restore its saved scroll position and drafts. Settings input MUST NOT change the session title filter. This is not a GNOME lifecycle requirement.

Acceptance: open each tab without increasing the native window count; switch Telegram between connected/setup/connected without blank content or losing the token draft; type in the token field, Tab out, and Escape back to the original session scroll offset. The native offscreen renderer checks these outcomes in both appearances. Native NSMenu tracking, clipboard/IME, VoiceOver and OS activation still require interactive runtime verification.

## Defaults and persistence ledger

M NSUserDefaults: KnownApplications(JSON string), AnimateMenuBar(defaulttrue), MenuShortcut(optional encoded), LaunchAtLoginEnabled plus actual SMAppService status. Legacy domain migration copies missing values once but not OS notification authorization/first-launch results. Setup keeps IntegrationSetup.<agent>, error strings, notification error, FirstLaunchSetupCompleted. Tokens via Security.framework Keychain. Shared domain default loginDisabled, animationtrue, shortcutNone, empty catalog.

G preferences.json under state directory: applications,animation,shortcut; corrupt/missing file falls back to defaults. Login determined by existence of `$XDG_CONFIG_HOME/autostart/ai-agent-monitor.desktop` (default~/.config), created/removed by control. Token via `secret-tool` Secret Service, never JSON; missing/locked keyring yields explicit error. Telegram nonsecret config in state `telegram.json`. State home M `~/Library/Application Support/AI Agent Monitor`; G `$XDG_STATE_HOME/ai-agent-monitor` or `~/.local/state/ai-agent-monitor`. ## Web pane (macOS)

The fifth tab controls the resident HTTP server. M uses a460pt-wide natural-height pane:426pt plus34pt per Cloudflare/interface row, the heights of the two account-backed sections (34pt collapsed each), and an optional40pt error row. While off it collapses to92pt (132pt on startup error), showing only the title, switch and subtitle. Enabling starts the local listener on `0.0.0.0:8765`, attempts Cloudflare and loads saved ngrok/Tuna credentials independently; disabling stops all paths and disconnects browsers while preserving authorization. Web access starts off on each application launch. IPC runs off the AppKit thread; status polling every two seconds preserves selection, expansion and token drafts.

M and H show one connection-method list: ngrok, Tuna, Cloudflare, Local network and This computer. Multiple bound network interfaces remain individually selectable in M, with their URL in the tooltip. A radio is enabled only when its route exists. The provider name follows the radio; ngrok/Tuna have an independent28×28pt circular disclosure immediately after the name. Muted right-aligned status says **ready** for every usable route; other states are **not configured**, **connecting…**, **connection failed**. The chosen route controls the QR, link and privacy instructions. A newly appearing HTTPS origin is selected automatically; otherwise retain selection by URL, including after interface reordering. No inner scroller is used; the popup grows until the outer settings viewport needs to scroll.

Below the list, a thin separator precedes the selected URL, displayed without its pairing secret. The URL is underlined, clickable, uses a pointing-hand cursor and has no background hover. Clicking opens the full pairing link; the adjacent icon-only Copy button copies that same full link. The next row contains the120-second progress bar, remaining seconds and an icon-only regenerate button. Both buttons occupy the same right-aligned28×28pt circular hover/focus surfaces as disclosures; icon color is secondary, and symbols are14px in H (native SF Symbols in M). H uses a2px gap between these rows; M uses adjacent28pt controls on30pt row centers. A200×200pt black-on-white QR follows alongside route-specific instructions. Paired-browser count and disconnect explanation follow compactly, without a reserved empty footer.

QR, opened link and copied link MUST use the same selected address and single-use token. The visible URL and tooltip MUST omit the token. Renewal invalidates the previous token while preserving paired browsers. An expired/consumed token disables link/Copy and triggers renewal while the pane is visible. M retains the previous QR while the replacement is in flight; this does not make the old token valid. Errors appear inline and renewal retries with normal polling. A server stop hides the whole connection area and disconnects browsers while preserving authorization. QR modules remain absolute sRGB black in both themes. Sources: `WebSettings::{render,refresh_countdown_at,draw_qr}`, `RemoteTunnelSettings::{render,set_route}`, `InlineSettings::{style_actions,paint_at}`, `src/web/settings.js::webPane` and `src/web/monitor.css`.


GNOME currently exposes management through CLI (`web tunnel-start` / `web tunnel-stop` for remote mode) rather than a settings tab; the prototype now has five simulated panes, including Web. Its Web pane starts disabled, automatically simulates a Cloudflare connection and a saved-token ngrok connection after enabling Web access, and shows inline LAN/loopback/remote radio addresses, a QR and a120-second renewing countdown. QR fixtures encode reserved example addresses; Copy link matches the selected fixture. Demo renewal alternates two synthetic tokens and does not implement authentication. No service starts and no network pairing occurs. Telegram setup simulates checking and waiting for activation; Open bot completes that activation, and Cancel during replacement keeps the old bot. Unlink is immediate, matching the native control. The settings container receives focus on entry without highlighting Back. The remote HTML host hides those mock settings controls. Browser behavior, expiry, persistence, errors and transport bounds: [Web access](../../web-access.md). Sources: `src/macos/web_settings.rs`, `src/web/server`, `src/macos/menu.rs` settings navigation; native visual and web transport tests.

### ngrok disclosure and simultaneous tunnel addresses

M and H initially collapse each account-backed section in the connection-method list described above. Only the separate chevron toggles details; selecting the radio changes the destination without changing connection configuration. Polling preserves expansion and input drafts. Native expanded accessibility state and HTML `aria-expanded`/`aria-controls` expose the disclosure state. Expanded details have a1px downward-fading thread line and14px content inset, and resize the outer settings document.

| Status | Collapsed title | Expanded token row | Actions |
|---|---|---|---|
| No saved credential | ngrok — not configured | Token label above editable secure field, placeholder Paste token | Connect; key/browser-arrow opens the personal account dashboard |
| Connected | ngrok — ready | Token: stored securely in macOS Keychain, secret never loaded into a field | Change; no Connect button |
| Failed with saved credential | ngrok — connection failed | Token: stored securely in macOS Keychain | Change and Reconnect; failure detail appears beneath |
| Failed before credential storage | ngrok — connection failed | Editable secure field | Connect; inline failure detail |
| Startup/recovery in progress | ngrok — connecting… | Saved-token caption when known, otherwise editable input | Connect disabled during startup |

Connect validates the token shape, stores it in a separate Keychain entry and starts the SDK asynchronously. A saved token is loaded on enabling Web access; absence is normal, does not show an error or invalidate the existing local QR. The SDK needs no separately installed ngrok program. Reconnect only replaces the ngrok path and disconnects its browsers while preserving authorization. Cloudflare starts independently and remains available during ngrok setup/failure. Stopping Web access stops all providers.

The address list is the union of connected Cloudflare, ngrok and Tuna HTTPS origins plus reachable bound-interface HTTP addresses and loopback, each represented by its method name, URL tooltip and availability status. Neither provider hides the other. A new HTTPS origin is selected automatically; otherwise status updates preserve the selected URL. QR, copy destination and privacy instructions refer to the selected address. Missing/failed origins are removed. LAN, Cloudflare and ngrok browser authority are separate; a cookie cannot cross ingress. A provider outage/restart does not revoke another provider's browser. Token renewal keeps established devices connected.

M and H place a key + external-browser-arrow button immediately after the unconfigured token input, before Connect. Its tooltip/accessible label explains opening the ngrok dashboard; activation emits a browser link to the personal authtoken page. It has no separate Get token text button. The two glyphs are16px in H; M uses a36×16pt composite asset. Connect is disabled until the input contains non-whitespace text and updates immediately during editing without recreating the field. Reconnect with a saved credential does not require new input. Before configuration, the caption **Will be stored securely in macOS Keychain** appears below the token input, aligned with its left edge rather than the Token label. M and H place the Token label above the input. With a saved token, both replace the field with `Token: stored securely in macOS Keychain` and Change; the token is never revealed. Change opens an empty replacement input while keeping the current connection until Connect. Cancel discards the replacement draft and restores the saved-token row. Reconnect remains available on connection failure. H uses reserved example origins and synthetic credentials. Entering `invalid` in its first token setup simulates a connection failure with a saved credential so Reconnect can be demonstrated; it never contacts ngrok or stores a real token. Re-enabling Web access reuses the synthetic saved flag. G manages the same backend via CLI; native ngrok onboarding remains absent. See [setup and transport details](../../web-access.md#remote-access-with-ngrok).
