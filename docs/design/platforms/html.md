# Interactive HTML frontend supplement

The current preview is a thin mock host for the HTML prototype component, not a separate copy of the UI. The product document, CSS and interaction handlers live in [src/web](../../../src/web/README.md). [monitor-ui.html](../../../design/previews/monitor-ui.html) embeds that document; [mock-data.js](../../../design/previews/mock-data.js) supplies fixtures, simulated answers/navigation and theme changes; [mock.css](../../../design/previews/mock.css) supplies the fake system panel. No CDN scripts or runtime icon downloads are used.

<a id="html-authority"></a>
## Implementation and scope

The preview remains the primary visual reference. The component behavior is implemented in `AAMMonitor.mount` and its returned methods; host-only effects are simulated by `mock-data.js`. The native application uses AppKit/GTK and has no web window. An optional resident HTTP host now serves this same renderer to external browsers; see [Web access](../../web-access.md). Discovery, native notifications, Telegram and full settings are not simulated as working production services.

<a id="html-state"></a>
## Fixture host

The host supplies VS Code, Terminal and Codex sessions, an approval with long command/scoped action, a two-question form, working/finished status and a fixed85% weekly quota. Request contexts are distinct fixture values. Answers mutate fixture status/message; opening a title changes the displayed preview version; finished acknowledgement changes the fixture to Idle. Previous-message actions supply an example page. Settings opens the in-popup experiment described below. Quit/Close clears focus through the shared visibility contract; the fake panel's robot button reopens it. No production request is sent.

The appearance selector posts a new Light/Dark snapshot to the iframe. Parent and child verify each message's source window. The product's DOM, forms, filtering, focus, mesh, disclosure and responsive behavior all live in `src/web`; none of that code is loaded by the native application. Expansion/drafts are in-memory; the earlier standalone localStorage expansion adapter is no longer active. The fake panel's initial counters are illustrative and are not live monitor counters.

## Presentation and verification

The fake panel/iframe are at most460px wide; the frame follows the viewport height up to1100px. Product content scrolls inside its own list, continuing behind a floating quota footer. Measured bottom padding lets the final content scroll fully above the quota panel; the transparent overlay passes pointer/wheel input through to the list. The shared glass tokens and paths are in [glass surfaces](../components/glass-surfaces.md). The page does not emulate OS window/Dock positioning.

<a id="prototype-keyboard-and-filtering-revision-2026-11-08"></a>
## Keyboard and filtering revision

Shared `applyFilter`, `highlight`, `keyboardFocus`, `visibility` and product event handlers own keyboard behavior. Titles filter by case-insensitive AND words; Backspace removes a grapheme; Escape clears the query or requests Close. Title focus is the hover surface plus an outline. Radio/custom selection, single-question presets, secret input, two-line command disclosure and disabled submit are all shared behavior, not fixture-specific event handlers.

A hidden WebKit development check verifies the local preview iframe, fixture rendering, command disclosure and browser handlers without opening a visible browser. This is not a native application host or production integration test. Native accessibility/IME, AppKit/GTK parity and OS-owned menu/window behavior remain separate verification work.

<a id="html-component-contract"></a>
## Component state and interaction contract

- Parent-to-child snapshots contain fixture application IDs/icons, titles, status, optional requests, completion generations, safe message HTML, directory/branch/model, history and quota. `setSnapshot` keys DOM rows by session ID. Unchanged rows retain DOM; replaced rows restore drafts, selection and focus only while request context is unchanged. New request contexts expand the session. Resolving a request clears its answer focus without moving it to the header.
- Robot/chevron clicks and title Left/Right control disclosure. Title click emits `open`; direct finished-icon clicks emit `seen`. Disclosure/history/title actions include the fixture completion generation when acknowledging Finished. The mock host supplies the visible outcome; it never opens a real session.
- Filtering matches every whitespace-separated title word, case-insensitively, highlights merged ranges, hides empty application groups and shows the query in the footer. Empty results read “No matching sessions”. Input/password editing does not filter. Up/Down traverse visible enabled titles/actions/answer inputs. Left/Right cycle actions only when they share a horizontal line. Escape clears the query, otherwise emits Close.
- Single questions use preset buttons; freeform adds an input and Send answer on one line. Multiple questions use separate radio groups and one submit. Typing or Enter in a custom input selects it without submitting. `freeform=false` omits the own-answer control; secret inputs use `type=password`. Missing required answers, disabled requests and Sending/Reconciling states disable submission. Unsupported question capabilities offer “Answer in editor…”, which is a preview navigation event.
- The exact command and each scoped-action prefix are separate selectable blocks. Two content lines are initially visible. Disclosure appears only on overflow, expands in place and is excluded from Tab/custom traversal. Copy emits the entire original command text.
- Sending/Reconciling display “Sending…”/“Checking delivery…”. Supplied errors and unavailable live-state explanations have rendering branches. These messages are demonstrated input states, not proof of delivery. No click itself grants a real permission or executes a command.
- History pages are supplied by the mock host. Loading/exhausted/error branches and cached-page reveal are local component behavior. Earlier messages have filled markers; previous-message hover follows the first message's vertical region. No remote message image is fetched.
- Enabled interactive controls share the title's glass hover surface: `--aam-hover-surface` (cool/violet radial reflections and the 110° blue-violet gradient) and `--aam-hover-shadow` (inset edges and soft outer shadow). This applies to robot/disclosure buttons, clickable Finished, header actions, request actions, command copy/disclosure, history, answer labels and links. Existing control geometry and semantic status colors are retained. Disabled controls do not acquire hover decoration. This is an HTML prototype convention; native supplements describe their own implemented styling.
- Product mesh and header wave scroll with the content; the quota footer overlays the list at the bottom of the window. The list extends behind it and has bottom padding/scroll padding based on the measured footer height. `layout` coalesces geometry work in microtasks. `visibility(false)` clears focus/filter and pauses animation; component drafts and disclosure remain in memory until the page is destroyed. The host's fake panel button restores visibility.

Sources: `src/web/monitor.js` `mount`, `setSnapshot`, `preserve`, `restore`, `requestMarkup`, `applyFilter`, `keyboardFocus`, `layout`, `visibility`; `src/web/monitor.css`; `src/web/index.html`; `design/previews/mock-data.js`. Preview events use source-checked parent/iframe messaging only; the former native script-message bridge, CLI entry point and Rust snapshot projection have been removed.

Prototype footer surface revision: the floating footer is transparent, while the quota capsule has an opaque theme-specific gradient base with decorative light pools. Content continues behind the capsule but cannot show through its interior. The capsule retains its continuous gradient rim via a masked pseudo-element and has no quota-card shadow. The progress track/fill and labels retain their existing styles. Source: `src/web/monitor.css` `.aam-footer`, `.aam-usage`, `.aam-usage::before`.

Prototype answer focus: keyboard-focused answer text, single-question preset buttons and other enabled controls use the shared glass hover surface with a 2px theme-specific outline and 1px offset, matching title focus. Radio inputs retain their native selected/unselected artwork but have no separate focus outline/shadow. The custom field has no hover decoration and retains its resting fill during keyboard focus, adding only the same outline. Its own-answer radio is excluded from Tab and Up/Down traversal, so navigation enters the text field directly. This does not change which radio is checked. Source: `src/web/monitor.css` `--aam-key-focus` and the keyboard-focus selectors.

Primary approval actions are an exception to the generic glass fill: HTML and AppKit retain the blue-violet gradient and white caption on hover and keyboard focus. Hover brightens the gradient; keyboard focus adds the outline, including while hovered. Neither state changes enabled status. Sources: `src/web/monitor.css` primary-action selectors; `src/macos/visual.rs` `GlassBox::draw_glass`, kind 4; `src/macos/menu.rs` `apply_hover`. GNOME uses its native button feedback.

## In-popup settings prototype — updated 2026-11-14

This prototype demonstrates in-popup settings; macOS now implements the same shell with real native controls, while GNOME retains a separate settings window. The header gear replaces the session list and quota footer with Settings inside the same popup. A Sessions back button or Escape restores the list, its scroll offset, disclosure and drafts, and returns focus to the gear. The hidden list is inert. Closing the popup exits settings. The last selected settings tab remains local to the component.

General, Applications, Agents (robot), Telegram and Web (network) use a five-column icon-and-label tab strip. Opening Settings focuses the container without assigning keyboard focus to Back. Left/Right and Home/End move between focused tabs; Tab/Shift-Tab wrap among visible enabled settings controls. Settings keystrokes never enter the session title filter. The surface uses existing mesh/glass tokens and theme outlines; content scrolls inside the popup, including long Telegram setup. Header/version and navigation scroll with it. Width follows the popup; below360px form rows wrap.

General provides native-style mock login and eye-animation checkboxes plus an in-memory shortcut recorder. Animation and application switches send a `preferences` preview event to the fixture host, which actually filters fixture sessions and updates the animation flag. The application catalog retains hidden applications. Login and shortcuts do not register with the OS. Agents shows installed Codex/Claude fixtures and simulates Check & set up feedback.

Telegram begins with a fictional connected bot, Test/Open beside its name, and Change bot/Unlink bot beneath. Unlink is immediate, matching the native action. Setup includes selectable read-only suggestions, username regeneration/copy, a single-line password token input/Paste, validation, checking and waiting-for-activation states. Open bot appears only when activation is ready, and simulates completing activation. Cancel during replacement, including after token validation, restores the existing bot. The replacement warning is absent during initial setup. Failed validation preserves the draft. BotFather/Open/Test are local preview feedback, not external launches or network requests. Token data is not emitted to the host or persisted, and no Keychain operation occurs. The Keychain copy illustrates the macOS setup text. All mock state resets on reload.

While Web is off, the preview shows only its title, switch and subtitle; no empty pairing area, disabled QR/link buttons, browser count or disconnect note remains. Web starts off and uses one Web access switch to simulate enabling the listener and automatically starting Cloudflare, local/loopback/remote inline radio addresses and automatic selection of a newly connected HTTPS origin. A200px black-on-white QR and120-second countdown remain visible while enabled. New QR and expiry renew the fixture; Copy link reflects the selected address and the visible code. Valid QR fixtures encode reserved example addresses and alternate two demo tokens; no real pairing or credential security is implemented by the prototype. Local addresses remain available alongside the remote address. Turning Web off removes all paths and the QR, including when a connection is still starting. There is no separate Remote access switch.

Sources: `src/web/settings.js` `AAMSettings.mount`; `monitor.js` settings routing/lifecycle; `monitor.css` prototype settings rules; `design/previews/mock-data.js` preferences handler. A hidden WebKit check passed for both themes, five tabs, the single Web access switch and automatic tunnel startup, inline address selection, renewing QR countdown, application filtering, animation, shortcut recording, invalid-token feedback, cancellation, arrow navigation and return to the session list. Native production setup and real Telegram delivery are outside this experiment.

## Live HTTP host revision — 2026-11-13

The shared renderer now also has a production HTTP host, separate from the iframe fixture host. `remote.js` pairs by one-time fragment token, uses an HttpOnly session cookie, receives an initial keyed snapshot and revisioned diffs over WebSocket and submits typed HTTP commands. Previous-message requests and their admission/error replies use the existing authenticated WebSocket; loaded history arrives through state diffs. `stream.js` atomically reconstructs ordinary renderer snapshots; a revision mismatch disables stale controls and requests a complete replacement. Unchanged state produces no data update. Standard negotiated WebSocket compression is transparent to the renderer; HTTP assets negotiate gzip separately. The host disables stale controls on disconnect and reconnects on foreground return. The preview-only settings gear is hidden, the power action logs out the browser, and title navigation targets the host computer. `remote.css` fills a dynamic phone viewport. Static files are embedded in the resident binary; no WebView is added to the native frontend. Transport contracts and the explicit remaining platform/runtime gaps are in [Web access](../../web-access.md). Public tunnels remain a separate unimplemented plan.
